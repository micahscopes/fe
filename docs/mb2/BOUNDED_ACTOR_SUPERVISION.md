# Fe-owned structured child supervision

Worker lifecycle policy belongs to Fe. The fixed browser runtime owns only the
mechanics that require browser objects: construct one Module Worker, transfer
its ports, report readiness or failure, retire it, and perform an explicit
restart or close requested by its caller.

`createModuleWorkerActor` and `createCanonicalModuleWorkerActor` therefore do
not accept restart windows, clocks, backoff values, observers, or timer hooks.
They never construct a replacement after a startup or runtime failure. A
runtime crash immediately closes the endpoint, fails in-flight requests with
`FE_ACTOR_WORKER_RUNTIME`, releases auxiliary capabilities, terminates the
Worker, and enters a stable failed state. An explicit `restart()` is the only
mechanical route to a replacement.

The pure policy lives in `std::runtime` as `RestartWindow`,
`ChildSupervisionState`, `ChildLifecycleEvent`, and `ChildSupervisionStep`.
Given a lifecycle fact and the parent scope's state, Fe selects exactly one of:

- no action;
- spawn now;
- restart after a typed delay;
- close because the parent was cancelled; or
- fail because the bounded restart budget was exhausted.

The rolling-window calculation, epoch advancement, startup/runtime failure
classification, backoff choice, exhaustion, terminal inertness, and
parent-cancellation propagation are all ordinary Fe data and control flow.
Browser clocks and timers will remain handler capabilities, but their readings
are inputs to this reducer rather than JavaScript policy.

Three independent gates protect the boundary:

- `module-worker-lifecycle.test.mjs` proves that fixed JavaScript performs
  exact Worker and port mechanics, never auto-spawns, fences epochs, preserves
  affine transfer ownership, handles restart races, and accepts no
  `supervision` option.
- `worker_supervision_policy.rs` compiles the ordinary Fe reducer to Wasm and
  executes it in Wasmtime against explicit semantic expectations for spawn,
  readiness, rolling-window reset, bounded backoff, exhaustion, terminal
  inertness, and parent cancellation. Generated bytes are not its oracle.
- `worker_scope_runtime.rs` compiles the complete `ChildPlacement<B, C>` Fe loop
  through the production suspension/re-entry machinery. A fixed broker supplies
  only unit-valued spawn, failure-observation, and close mechanics. Explicit
  tapes prove Fe alone selects epochs, timer-backed restart, exhaustion,
  transport-failure meaning, and exactly-once cancellation cleanup.

`C` is the nominal child program type. The zero-lane completion payloads are
`ChildStarted<C>` and `ChildRuntimeFailure<C>`, so distinct child scopes remain
different Fe handler identities without a runtime ID, URL, or manifest field.

This is not yet the completed structured-scope feature. The target-neutral
effect, owning Fe loop, and `createCanonicalBrowserWorkerScope` adapter are
landed and compiler-packaged. The adapter maps each Fe-selected epoch to exactly
one initial construction or successor restart and exposes abortable runtime
failure observation. Remaining work must publish distinct parent-scope and
child-actor Wasm artifacts, attach that capability from the immutable package,
and prove it in Chromium. Rich message values and nested child scopes remain
later compiler-derived layers. JavaScript must not recreate supervision policy
around the mechanical operations in the meantime.
